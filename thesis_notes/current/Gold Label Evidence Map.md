## Why This Matters

The thesis must justify that the benchmark tests semantic confusion under procedural distinction:

> alternatives should sound relevant, but the gold skill should be procedurally more suitable.

Operational definition:

A gold-label skill is the skill that should be selected if the selector correctly interprets the user's procedural requirements, not merely the skill with the closest name or most similar description.

A gold label is valid when:

- the skill's use conditions, input/precondition, workflow, output artifact, and success criterion match the request;
- at least one concrete prompt requirement explains why the gold is better than its listed alternatives;
- alternatives are semantically plausible but procedurally different;
- the gold skill is atomic enough to be a single selected capability, unless the prompt explicitly asks for broad routing;
- the prompt does not leak the exact skill name or unique copied phrases;
- the label is a defensible primary workflow choice; strict-gold validity does not assert that it is the only acceptable skill in the entire library.

That justification needs evidence at two levels:

1. Prompt-level: why this gold skill fits this user request.
2. Pair-level: why each listed alternative is plausible but less suitable.

## Public-Gold Example

Public-gold prompt `public_gold_p01_pdf_extraction` already includes thesis-ready evidence:

- Prompt: extract native text, table cells, and metadata from a non-scanned PDF into structured JSON with page anchors.
- Gold skill: `public-office-pdf-extraction`.
- Gold rationale: the skill targets native PDF text/table/metadata extraction, not Q&A, OCR, or conversion.
- Field axes: `input_or_precondition`, `output_artifact`, `workflow_or_procedure`.
- Alternatives: `public-office-chat-with-pdf`, `public-office-pdf-ocr`, `public-office-pdf-converter`, `public-openai-pdf`.

This is a good thesis example because the alternatives are semantically plausible but procedurally different:

- PDF Q&A changes the interaction mode.
- PDF OCR assumes scanned/image input.
- PDF conversion changes the output artifact.
- Generic PDF handling is broader and less procedure-specific.

## Controlled Example

Controlled prompt `api_p1_openapi_contract_review` stores prompt/gold/alternatives in `skill_benchmark/prompts/api_backend_design_confusability.json`:

- Prompt: review `billing_openapi.yaml` as an API contract, focusing on schemas, examples, status codes, auth behavior, pagination, and client compatibility.
- Gold skill: `openapi-contract-reviewer`.
- Alternatives: `external-api-integration-planner`, `webhook-contract-planner`, `architecture-boundary-reviewer`.

The narrative rationale is not stored inline in the prompt file. Evidence is spread across validation outputs:

- `procedural_distinctness_report.json` records pairwise differences on axes such as input/precondition, output artifact, workflow/procedure, dependency/resource, and boundary signal.
- `procedural_requirement_alignment_report.json` records the gold rank among listed candidates and the score margins.
- `R2_structured_procedural.jsonl` and `R3_dependency_resource_aware.jsonl` store the extracted fields for each skill.

Thesis-ready rationale:

> The prompt asks for endpoint-level OpenAPI contract review, including schema, examples, status codes, authentication behavior, pagination, and client compatibility. `openapi-contract-reviewer` is the gold because its procedure inspects an already-authored API contract for correctness and compatibility issues. `external-api-integration-planner` is plausible because it mentions APIs and external systems, but it plans integrations rather than reviewing an existing contract. `webhook-contract-planner` is plausible but targets event/webhook payload contracts. `architecture-boundary-reviewer` is broader system design review rather than endpoint-level contract inspection.

## Current Gap

Controlled prompt files currently do not include explicit `gold_rationale`, `field_axes`, or per-alternative `rejection_rationale` fields. The evidence exists, but it is split across prompt JSON, representation JSONL, and validation reports.

For thesis writing, this is acceptable if we cite the validation pipeline. However, for readability and defence, we should generate a small thesis-ready evidence table with 8-12 representative cases.

Additional RQ1 gap, 2026-06-23:

The current benchmark validates semantic confusability and procedural distinctness, but it was not originally designed as a clean field-targeted RQ1 experiment. Existing prompts often involve several distinguishing fields at once. This is useful for realistic routing and RQ2 strategy comparison, but weaker for claims such as "the output field helps more than the workflow field."

Active RQ1 split:

- **RQ1a:** individual field discriminability. Use field-targeted test units to check whether one skill-side field value helps select the correct near-neighbour skill when shared context is controlled.
- **Supporting RQ1b audit:** field prevalence and recoverability. Use corpus audits and extraction QA to check whether controlled, public-gold, and external skill corpora actually contain recoverable evidence for the operational fields. **RQ1b naturalistic replication:** use frozen original-artifact clusters with model-assisted acceptable-set curation for a later selection study; Wave 001 is original-only, not causal field-masking evidence.
- No RQ1c is currently defined.

For RQ1, each thesis-ready case should additionally record:

- `primary_distinguishing_field`;
- `secondary_distinguishing_fields`;
- the exact prompt phrase that requires the primary field;
- exact gold-skill evidence for that field;
- the reason each alternative is weaker on that field;
- a controlled skill-side baseline description that keeps shared task context but masks the primary field;
- a leakage/stability status such as `clean`, `leaky_original_description`, `too_vague`, or `multi_field`;
- whether the same case should be used for RQ1 field ablation, RQ2 strategy comparison, or both.

Prompt-side rule:

- The user prompt should explicitly state the operational requirement needed for a stable gold label.
- Do not make the prompt vague to avoid leakage. Vague prompts such as "help with this PDF" are not valid RQ1 cases.
- Leakage control belongs to the skill-side baseline: the baseline should preserve shared cluster context while hiding the primary field.
- The shared context may name the broad task family, such as PDF extraction or API review, but must not name the target field value, such as scanned/native, JSON/prose, validate/repair, no-legal-advice/legal-advice, HF Jobs/local, or visual-evidence/data-scrape.
- If the original skill description already leaks the primary field, keep it for realistic RQ2 reporting but create a controlled masked baseline for RQ1.

## RQ1 Field-Targeted Example Cases

These are the kinds of cases that should be selected or authored before making strong field-importance claims:

| Primary field | Example gold vs alternatives | Test prompt shape | What the field should prove |
|---|---|---|---|
| `use_condition` | OpenAPI contract reviewer vs external API integration planner vs webhook planner. | "Review this existing OpenAPI contract for schema/status/auth/client compatibility." | The correct skill is selected because the task is review of an existing contract, not planning an integration. |
| `input_precondition` | Native PDF extractor vs PDF OCR vs PDF Q&A. | "Extract selectable text, embedded table cells, and metadata from a non-scanned PDF." | The correct skill is selected because the input is native/selectable PDF, not scanned image PDF. |
| `output_artifact` | PDF table extractor vs PDF summarizer vs PDF converter. | "Return structured JSON/CSV tables with page anchors, not a prose summary." | The correct skill is selected because the requested output artifact differs. |
| `workflow_procedure` | Dataset validator vs dataset repairer vs anomaly explainer. | "Check schema/ranges/missingness and report validation failures before changing the file." | The correct skill is selected because the procedure is validation-first rather than repair/explanation. |
| `boundary_not_for` | Compliance triage vs legal advice writer vs policy summarizer. | "Flag compliance risks without giving legal advice." | The correct skill is selected or unsafe sibling rejected because of a negative boundary. |
| `dependency_resource` | HF Jobs runner vs local experiment runner vs model-card writer. | "Run this experiment on Hugging Face Jobs with GPU and persist artifacts." | The correct skill is selected because a platform/resource dependency is required. |
| `success_verification` | Browser visual QA vs browser scraper vs UI debugger. | "Verify the rendered page has no overlapping text and capture evidence." | The correct skill is selected because success requires visual verification, not data extraction. |

These examples should be used as patterns, not necessarily final prompt text. Final cases must pass the existing integrity, procedural-distinctness, semantic-confusability, and leakage checks.
