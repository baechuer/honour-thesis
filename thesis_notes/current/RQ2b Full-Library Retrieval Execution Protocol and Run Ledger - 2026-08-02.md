## 1. Research Question and Study Boundary

RQ2b asks:

> When the candidate set is not guaranteed, how do compact discovery metadata, original full skill artifacts, and explicit operational-fact representations interact with lexical retrieval, dense retrieval, and fixed-candidate reranking?

The minimal study has two linked stages:

1. **B1 candidate generation:** retrieve from the complete 2,433-skill library and measure whether the frozen strict gold skill survives into the candidate set.
2. **B2 candidate ordering:** independently rerank each exact persisted candidate set with the SkillRouter and Qwen rerankers, then measure conditional and end-to-end selection accuracy. Both receive the same B1 Top-20 list; their scores and costs are never pooled.

This study does not retrain a retriever or reranker. It does not evaluate graph/tree routing, downstream task execution, or the external 79K SkillRouter corpus. The prospective B0F-A1 amendment adds the released SkillRouter embedding checkpoint as a third first-stage retriever on this frozen corpus. The proposed B0F-A2 amendment adds generic Qwen `qwen3-rerank` as a required, separately reported B2 comparator alongside the skill-specific SkillRouter reranker over the same persisted Top-20 candidate sets; the two are never ensembled. The proposed B0F-A3 amendment adds a blinded pre-retrieval gold-validity audit so that label coverage is checked before candidate-generation results are interpreted. None of these amendments changes the eight Qwen-centred primary hypotheses until it has independently passed review, exact approval, and sealing.

## 2. Evidential Status

The local benchmark has been used in historical exploratory retrieval runs. A new split cannot erase that exposure. RQ2b is therefore a **prospectively frozen internal re-evaluation on historically explored prompts**. It is not an untouched confirmatory test, and conclusions are bounded to this corpus.

The new I3C and I3-flat representations, provenance-correct source inventory, candidate persistence contract, exact-source equivalence closure, and complete B1/B2 pipeline have not previously been evaluated together. All RQ2b outputs must be generated after protocol freeze by new versioned runners. Historical outputs may motivate expectations but may not be copied into the RQ2b result matrix.

## 4. Representation Contract

All four representations have one row per `skill_id`. Gold, alternative role, prompt family, benchmark stratum, and source origin are metadata only and must never enter selector-visible text.

### 4.1 I1-discovery

Selector-visible text:

```text
name: <source-native frontmatter name>
description: <source-native frontmatter description>
```

I1 excludes benchmark slugs, benchmark family labels, normalised-wrapper descriptions, generated dependency profiles, and generated tags. This matches the practical progressive-disclosure metadata available in the approved source artifact while avoiding benchmark-specific leakage.

### 4.2 I2-original

Selector-visible text is the complete approved source artifact, byte for byte. No generated header, summary, wrapper, or field card is prepended. Processing may split an overlength artifact into lossless chunks, but it may not delete or silently truncate source content.

### 4.3 I3C-fielded

I3C is extracted only from the exact I2 text by the frozen `I3C_SUBAGENT_EXTRACTION_V2` prompt. The extraction retains both a normalized parser statement and an exact evidence quote, but **only the evidence quote is selector-visible**. Selector-visible serialization is:

```text
name: <same source-native name as I1>
description: <same source-native description as I1>

Use condition:
- <whitespace-normalized exact evidence span>

Input / precondition:
- <whitespace-normalized exact evidence span>

...remaining non-empty fields in canonical order...
```

Canonical field order is use condition, input/precondition, output/artifact, workflow/procedure, dependency/resource, boundary/not-for, success/verification. Empty fields are omitted. Selector-visible evidence serialization is byte-deterministic after UTF-8 decoding:

1. assert the worker's evidence string is an exact Python substring of the decoded I2 text;
2. replace `CRLF` and lone `CR` with `LF`;
3. apply Python Unicode-aware `re.sub(r"\s+", " ", evidence.strip())`;
4. preserve case, punctuation, and all non-whitespace characters;
5. compute the evidence source position with the first exact substring occurrence and order items within a field by `(source_position, item_id)`;
6. normalize the source-native name and description by the same whitespace rule and omit an evidence item only when its complete normalized span exactly equals the complete normalized name or description;
7. deduplicate normalized evidence globally across all seven fields: the first occurrence in canonical field order and then source order is retained, and every later exact duplicate is omitted.

The source-native name and description remain exactly the I1 values in their fixed serializer lines; only evidence bullets use the normalization above. `absent_fields`, generated normalized statements, confidence, warnings, parser identity, and QA metadata are not selector-visible. This prevents model-generated vocabulary and accidental term-frequency multiplication from advantaging either lexical or dense retrieval while preserving the extraction decision and explicit field organization.

### 4.4 I3-flat

I3-flat contains the same source-native name, source-native description, and exact selector-visible evidence spans as I3C-fielded. The seven operational labels and field boundaries are removed. Evidence spans are concatenated in canonical order as one neutral bullet list. No extraction is rerun and no text is paraphrased.

This is a matched-content test of operational field organization, not an independently extracted representation.

### 4.5 Excluded representation conditions

`I2+I3C`, I3H, I3M, R1-R4, graph edges, heuristic field cards, and the old generated public wrapper are excluded from the minimal core. `I2+I3C` may be proposed later as a deployment diagnostic only after B1/B2 are frozen.

## 5. I3C Construction and QA

### 5.1 Extraction inputs

Build one JSONL input row per source-inventory row containing only:

- `source_row_index`;
- `skill_id`;
- source-native `name` and `description`;
- `family` for identity alignment only;
- source path and source SHA-256;
- complete I2 text.

Workers receive no prompt, gold, alternative, result, or benchmark-role data.

### 5.2 Worker protocol

- use Codex subagents with low reasoning;
- each worker reads `skill_benchmark/extraction_prompts/I3C_SUBAGENT_EXTRACTION_V2.md`;
- use only the assigned input artifact text;
- output exactly one JSON object per input row;
- flush every 10 completed rows;
- dynamically chunk the input inventory at no more than 50 rows and no more than 60,000 approximate source tokens per chunk;
- keep at most six active workers;
- close every completed or failed worker before assigning replacement work;
- never reuse I3H, I3M, or external-corpus I3C rows.

### 5.3 Automatic acceptance gates

- 2,433/2,433 output rows;
- zero JSON parse failures;
- zero missing or duplicate `skill_id` values;
- exact `source_row_index`, `skill_id`, source path, and source-hash alignment;
- every non-empty evidence quote is an exact substring of its assigned I2 source;
- every selector-visible field item is produced only by whitespace normalization of that exact evidence quote;
- zero selector-visible evidence spans exactly duplicate the normalized source-native name/description or an earlier retained field span under the frozen global policy;
- unsupported/heading-only evidence is removed, not repaired by invention;
- serializer emits 2,433 I3C and 2,433 I3-flat rows;
- I3C/I3-flat selector-visible evidence-span multisets match exactly per skill;
- no selector-visible QA metadata;
- no benchmark role/gold/stratum leakage;
- field coverage, absent-field, warning, length, duplicate-text, and heading-frequency reports are persisted.

### 5.4 Manual QA

Before retrieval, review at least 120 stratified rows. Reviewers receive source text, extracted fields, and evidence mapping, but remain blinded to prompts, gold/alternative roles, benchmark strata, and all retrieval outcomes. The sample covers:

- authored and public-original sources;
- eventual gold, hard-neighbour, and background roles through a sample selected by a separate blinded sampler after extraction, without exposing those role labels to the reviewer;
- short, median, p95, and longest documents;
- sparse and dense I3C cards;
- every operational field;
- every warning class.

Critical errors are identity mismatch, benchmark-role leakage, non-substring selector text, or unsupported evidence; any critical error rejects the extraction version. A major error is a selector-visible span assigned to the wrong operational field or a generic/non-routing span likely to alter retrieval. More than 5% reviewed rows with a major error, or more than 5% within any reviewed field stratum, rejects the extraction version. Any detected major-error pattern triggers a blinded corpus-wide audit of that field/warning class. Corrections must be deterministic, corpus-wide, source-grounded, hash-versioned, and followed by a fresh 120-row sample. Never selectively repair only sampled rows, and never use retrieval outcomes.

For a calibrated review packet, source evidence is the only selector-visible extracted content. Any normalised parser statement must be either omitted from the reviewer view or prominently labelled `non-selector-visible parser aid`; it must never be audited as a literal source-evidence claim. This clarification follows the v1.2 calibrated QA failure audit. It does not relax the literal-evidence gate or the major-error threshold.

## 6. Stage B1: Full-Library Candidate Generation

### 6.1 BM25

- one global 2,433-document index per representation;
- lowercase ASCII-alphanumeric tokenizer `[a-z0-9]+`;
- `k1 = 1.5`, `b = 0.75`;
- exact raw prompt text;
- deterministic tie-break by `skill_id`;
- persist top 100, complete gold rank, build time, query time, index bytes, and token counts.

BM25 indexes complete text and does not truncate I2.

### 6.2 Qwen dense retrieval

- provider: DashScope international OpenAI-compatible endpoint;
- model: `text-embedding-v4`;
- dimension: 1,024;
- score: cosine similarity;
- exact raw prompt text, embedded once and reused across representations;
- persistent cache keyed by endpoint, model, dimension, chunker version, and exact text;
- no automatic retries during the authorised run;
- persist request, token, text, cache-hit, latency, and cost ledgers.

Terminology is important here. Qwen `text-embedding-v4` is the scientific first-stage dense encoder: queries and document chunks are embedded independently and compared by cosine similarity. The `pipizhao/SkillRouter-Embedding-0.6B` checkpoint named below supplies only a pinned local proxy tokenizer for conservative chunk-budget auditing; its embedding weights are not used by the RQ2b Qwen condition.

#### Lossless long-document policy

The primary dense method is explicitly a **Qwen max-chunk multi-vector retrieval pipeline**, not a pure one-vector representation comparison:

- documented provider ceiling: 8,192 tokens per input text;
- local Qwen3-family proxy tokenizer only, not a retrieval encoder in this study: `pipizhao/SkillRouter-Embedding-0.6B`, revision `c03c9bcee9fce92ab0262bb6dcf54d174a8ba558`, `tokenizer.json` SHA-256 `def76fb086971c7867b829c23a26261e38d9d74e02139253b38aeb9df8b4b50a`;
- maximum chunk: 7,500 proxy-tokenizer tokens;
- adjacent overlap: 256 tokens;
- boundaries: greedily pack complete Markdown heading/paragraph blocks; hard-split only a block that itself exceeds 7,500 tokens;
- coverage: every source token must occur in at least one chunk and reconstructed non-overlap spans must equal the tokenized source;
- aggregation: maximum query-to-chunk cosine per `skill_id`;
- tie rules: earliest source chunk wins within a skill; `skill_id` ascending breaks equal skill scores.

A one-chunk document remains one vector. The offline token audit found a maximum of 8,272 proxy tokens, two sources above the documented provider ceiling, and three sources requiring the frozen 7,500-token policy. ### 8.2 B2 endpoints

For P1, define `delta = acceptable Recall@20(I3C) - acceptable Recall@20(I2)`. The frozen practical margin is 3 percentage points. Non-inferiority holds only if the one-sided 95% grouped-bootstrap lower bound exceeds `-0.03` in **both** strata. Cost is reported separately and is not folded into this statistical decision. The 3-point margin means tolerating no more than roughly seven controlled prompts or four public-gold prompts of absolute recall loss. A prospective independent-pair precision calculation shows that a one-sided 95% half-width is approximately 2.35/3.07 points at 5% discordance, 3.33/4.34 at 10%, and 4.70/6.14 at 20% for controlled/public respectively; grouped dependence may widen these intervals. The margin is therefore stringent and may yield an inconclusive result. It was retained as a practical quality bar, not selected to guarantee a positive claim, and was frozen by the approved B0F protocol.

### 8.4 Inference

- use paired prompt-level outcomes and report prompt-weighted percentage-point differences within each stratum;
- bind the grouping key for both strata to the exact hashed `group` field in `prompt_inventory.jsonl`; that field records the source `family`, source `source_family`, or an explicit stratum fallback in `group_source_field`;
- use 10,000-resample grouped **percentile** bootstrap intervals with seed `2026080201`, resampling whole `group` values with replacement and recomputing the prompt-weighted estimand; two-sided 95% intervals use the 2.5th and 97.5th percentiles, and P1's one-sided 95% lower bound uses the 5th percentile;
- use grouped paired sign-flip randomization with seed `2026080202`, flipping all prompt differences within a `group` together, with 100,000 Monte Carlo draws; P2 and P4 use the positive-direction one-sided statistic, while P3 uses the absolute two-sided statistic;
- compute Monte Carlo p-values as `(1 + extreme_draw_count) / (100000 + 1)`, where `extreme` means `T_draw >= T_observed` for P2/P4 and `abs(T_draw) >= abs(T_observed)` for P3;
- report equal-group-weighted estimates as a sensitivity, not the headline;
- Holm-correct the six P2/P3/P4 superiority/effect p-values; P1 uses the intersection rule that both separately estimated stratum bounds must exceed `-0.03`;
- report raw descriptive estimates for all secondary slices;
- do not treat a non-significant result as proof of equality;
- do not pool controlled and public-gold into one headline estimate.

Stress prompts receive descriptive top-ranked skill, acceptable-set coverage, score margin, and ranking stability only.

## 10. Hypotheses

- **H2b-Compression:** The v1.1 strict-only analysis will compare I3C-fielded with I2-original on strict Recall@20, strict Hit@1, strict MRR@10, and index-visible/reranker-visible text. The base-v1 acceptable-set non-inferiority margin is not silently inherited.
- **H2b-Discovery:** The v1.1 strict-only analysis will compare I3C-fielded with I1-discovery on strict candidate recall across the controlled and public-gold strata. No unannotated “description lacks evidence” subset is claimed.
- **H2b-Organization:** I3C-fielded versus I3-flat will depend on retriever architecture; labels may help lexical matching, add dense-embedding noise, or produce no material effect.
- **H2b-Retriever:** BM25 will be stronger for direct terminology, while Qwen will be more robust to paraphrase; the domain-tuned SkillRouter embedding replication tests whether representation ordering survives a skill-specific dense encoder. Representation ordering need not be universal.
- **H2b-Reranking:** SkillRouter and generic Qwen rerankers are separate B2 comparators over identical persisted Top-20 lists. Either may improve conditional ordering when the strict gold is already present, but neither can recover a first-stage exclusion. Compare conditional strict Hit@1, end-to-end strict Hit@1, regression rate, latency, visible tokens, and cost separately; no aggregate result establishes universal reranker superiority.
- **H2b-Cost:** I3C will reduce one-time embedding volume and per-query reranker volume relative to I2; its extraction cost will be amortized as the library serves more queries.

Null or reversed outcomes are valid. I2 winning would mean compression removed useful interactions. I1 matching I3C would mean source descriptions already carry sufficient routing evidence. I3-flat matching I3C would mean the extracted propositions, not literal field labels, do the work.
