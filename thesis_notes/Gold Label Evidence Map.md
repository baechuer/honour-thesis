# Gold Label Evidence Map

Last updated: 2026-06-06

This note records where gold-label justification, field axes, alternatives, and validation evidence are stored. Use it when writing the benchmark/methodology chapter and when selecting thesis examples.

## Why This Matters

The thesis must justify that the benchmark tests semantic confusion under procedural distinction:

> alternatives should sound relevant, but the gold skill should be procedurally more suitable.

Operational definition:

A gold-label skill is the skill that should be selected if the selector correctly interprets the user's procedural requirements, not merely the skill with the closest name or most similar description.

A gold label is valid when:

- the skill's use conditions, input/precondition, workflow, output artifact, and success criterion match the request;
- at least one concrete prompt requirement explains why the gold is better than its listed alternatives;
- alternatives are semantically plausible but procedurally different;
- the gold skill is atomic enough to be a single selected capability, unless the prompt explicitly asks for broad routing;
- the prompt does not leak the exact skill name or unique copied phrases;
- no unrecorded public/background competitor is clearly more procedurally suitable after full-library adjudication.

That justification needs evidence at two levels:

1. Prompt-level: why this gold skill fits this user request.
2. Pair-level: why each listed alternative is plausible but less suitable.

## Public-Gold Example

Public-gold prompt `public_gold_p01_pdf_extraction` already includes thesis-ready evidence:

- Prompt: extract native text, table cells, and metadata from a non-scanned PDF into structured JSON with page anchors.
- Gold skill: `public-office-pdf-extraction`.
- Gold rationale: the skill targets native PDF text/table/metadata extraction, not Q&A, OCR, or conversion.
- Field axes: `input_or_precondition`, `output_artifact`, `workflow_or_procedure`.
- Alternatives: `public-office-chat-with-pdf`, `public-office-pdf-ocr`, `public-office-pdf-converter`, `public-openai-pdf`.

This is a good thesis example because the alternatives are semantically plausible but procedurally different:

- PDF Q&A changes the interaction mode.
- PDF OCR assumes scanned/image input.
- PDF conversion changes the output artifact.
- Generic PDF handling is broader and less procedure-specific.

## Controlled Example

Controlled prompt `api_p1_openapi_contract_review` stores prompt/gold/alternatives in `skill_benchmark/prompts/api_backend_design_confusability.json`:

- Prompt: review `billing_openapi.yaml` as an API contract, focusing on schemas, examples, status codes, auth behavior, pagination, and client compatibility.
- Gold skill: `openapi-contract-reviewer`.
- Alternatives: `external-api-integration-planner`, `webhook-contract-planner`, `architecture-boundary-reviewer`.

The narrative rationale is not stored inline in the prompt file. Evidence is spread across validation outputs:

- `procedural_distinctness_report.json` records pairwise differences on axes such as input/precondition, output artifact, workflow/procedure, dependency/resource, and boundary signal.
- `procedural_requirement_alignment_report.json` records the gold rank among listed candidates and the score margins.
- `R2_structured_procedural.jsonl` and `R3_dependency_resource_aware.jsonl` store the extracted fields for each skill.

Thesis-ready rationale:

> The prompt asks for endpoint-level OpenAPI contract review, including schema, examples, status codes, authentication behavior, pagination, and client compatibility. `openapi-contract-reviewer` is the gold because its procedure inspects an already-authored API contract for correctness and compatibility issues. `external-api-integration-planner` is plausible because it mentions APIs and external systems, but it plans integrations rather than reviewing an existing contract. `webhook-contract-planner` is plausible but targets event/webhook payload contracts. `architecture-boundary-reviewer` is broader system design review rather than endpoint-level contract inspection.

## Current Gap

Controlled prompt files currently do not include explicit `gold_rationale`, `field_axes`, or per-alternative `rejection_rationale` fields. The evidence exists, but it is split across prompt JSON, representation JSONL, and validation reports.

For thesis writing, this is acceptable if we cite the validation pipeline. However, for readability and defence, we should generate a small thesis-ready evidence table with 8-12 representative cases.

## Recommended Thesis Examples

Pick examples from different domains:

| Domain | Example type | Why useful |
|---|---|---|
| PDF/document | public PDF extraction vs OCR vs Q&A vs conversion | Easy to explain semantic similarity and procedural distinction. |
| API/backend | OpenAPI contract review vs integration planning vs webhook contract | Shows input/output/workflow difference. |
| Browser/web | snapshot vs UI testing vs data extraction vs debugging | Shows same platform but different action and success criterion. |
| Data/spreadsheet | anomaly detection vs validation vs ranking vs reporting | Shows output/artifact and success-criterion differences. |
| Hugging Face/ML | dataset viewer vs model selector vs fine-tuning vs Space deploy | Shows dependency/platform and workflow distinctions. |
| Skill lifecycle | skill field audit vs hierarchy flattening vs installer vs benchmark evaluator | Directly relates to thesis topic. |
