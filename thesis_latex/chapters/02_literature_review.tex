\chapter{Literature Review}

\section{Skills as a Distinct Retrieval Target}

Skills should be treated as a distinct retrieval target, rather than as ordinary documents or larger tools. Documents are retrieved because they contain evidence that may help a model answer a question. Atomic tools are selected because they expose a particular callable function and argument interface. Skills sit between and beyond these cases. Like documents, they may contain natural-language instructions, examples, and reference material. Like tools, they may invoke scripts, APIs, resources, or other capabilities. However, their primary unit is neither a passage nor a single function call. A skill is a reusable procedural capability: it describes when a capability should be invoked, what input or precondition it expects, what workflow it follows, what dependencies or resources it uses, and what output or success condition it is meant to produce \cite{jiang2026procedural,jiang2026sok,anthropic2025skills}.

This procedural character is central in recent skill-focused literature. The procedural-memory survey frames skills as reusable memories of how to perform tasks, organised around acquisition, representation, invocation, and refinement \cite{jiang2026procedural}. The SoK on agentic skills similarly argues that skills are more than tools, plans, or memory items because they bundle executable procedural knowledge into reusable modules \cite{jiang2026sok}. These accounts suggest that skill selection should be understood as procedural suitability rather than topical relevance alone. A retriever that selects a document only needs to find material relevant enough to support the next reasoning step. A retriever that selects a tool must match an intended function and its arguments. A retriever that selects a skill must identify a procedure whose applicability, workflow, dependencies, outputs, and boundaries fit the user's intent. A selected skill can therefore be semantically relevant and still be procedurally wrong.

Early skill systems show why this distinction matters. SkillAct represents skills as textual abstractions containing a name, natural-language instructions, and example trajectories, and shows that such abstractions can improve agent performance in embodied tasks \cite{liu2024skillact}. Its design demonstrates that reusable procedural units can help an agent avoid repeatedly solving the same subproblem from scratch. However, SkillAct largely exposes the relevant skills directly to the agent and does not directly evaluate selection among many overlapping skills as the library grows. Voyager offers a stronger example of an expanding skill library: it stores successful behaviours as executable code and retrieves them from a library indexed by natural-language descriptions \cite{wang2023voyager}. This demonstrates the usefulness of persistent external skills, but it also illustrates the limitation of description-level retrieval. A description can identify a rough capability area, yet fail to preserve the operational distinctions needed when several skills use similar domain language but differ in input state, procedure, dependency, or output.

Filesystem-based skill libraries make the same issue concrete. A complete skill artifact may be a directory containing a \texttt{SKILL.md} file, scripts, templates, reference files, examples, or dependency instructions \cite{anthropic2025skills}. The selector, however, may initially see only a compressed representation such as a name and short description. This creates a layered retrieval problem: the stored artifact may contain rich procedural information, but skill retrieval may not see or use it. As a hypothetical illustration, consider three skills that could all be advertised as ``extract financial tables from a PDF''. One expects a born-digital annual report and uses the text layer plus table geometry to produce a CSV with page and cell coordinates. Another expects scanned statements and performs OCR cleanup before returning normalised JSON. A third takes an already extracted table and verifies each number against page-grounded evidence, returning an audit report rather than a fresh extraction. At the short-description level, all three concern financial tables, PDFs, extraction, and evidence. They are nevertheless not interchangeable, because they differ in input state, workflow, output artifact, dependencies, success criteria, and boundaries.

This distinction motivates the thesis terminology. A \emph{skill artifact} is the stored capability itself, such as a \texttt{SKILL.md} file, scripts, resources, examples, or generated program. A \emph{skill representation} is the selector-visible form of that skill, such as a short description, full text body, structured card, hierarchy node, or graph neighbourhood. \emph{Skill retrieval} is the process that uses those representations to produce candidates, rerank them, traverse an index, or load fuller skill instructions. Keeping these terms separate matters because a result may come from better artifact content, a richer representation, a stronger first-stage retriever, a reranker, or a more favourable evaluation setup. This thesis therefore treats skill retrieval as the problem of selecting a reusable procedural artifact through a representation that may or may not preserve the information required for correct invocation.

\section{Scale and Semantic Confusability}

Progressive disclosure is a useful practical response to context pressure. Anthropic's skill documentation describes filesystem skill artifacts that may include a \texttt{SKILL.md} file, scripts, resources, references, and dependency instructions, while the model initially sees compact skill metadata and loads the full artifact only when the skill appears relevant \cite{anthropic2025skills}. This avoids placing every full skill document directly in context. However, it does not remove the large-library routing problem. In a straightforward discovery setting, the agent still needs access to available skill names and descriptions so that it can decide which full artifact to load. As the library grows, even this compact discovery layer can consume context, increase prompt cost, slow selection, and create more opportunities for plausible but incorrect matches.

Benchmark evidence shows that scale is a real pressure in skill libraries. SkillsBench compares no-skill, curated-skill, and self-generated-skill settings across diverse tasks, and its most useful finding for this thesis is that smaller and more focused skill sets can outperform larger and more comprehensive collections \cite{li2026skillsbench}. This weakens the monotonic assumption that adding more skills always helps: usefulness depends on how tightly skills are scoped, represented, and made selectable. The single-agent skill-failure paper studies scale more directly by formalising skills as descriptor-policy-backend tuples and increasing the number of available skills \cite{li2026singleagent}. It finds that selection performance can remain stable until a threshold is reached, after which accuracy drops sharply. Crucially, that drop is linked not only to candidate count but also to semantic confusability among competing skills.

SkillRouter, SkillRet, and Skill Retrieval Augmentation make the same pressure concrete at large-repository scale, where an agent must identify relevant skills before downstream planning or execution \cite{zheng2026skillrouter,cho2026skillret,su2026sra}. SkillRouter treats routing as a large-scale retrieve-and-rerank problem over tens of thousands of candidate skills and shows that names and descriptions can under-specify the information required for correct selection \cite{zheng2026skillrouter}. SkillRet introduces a large-scale retrieval benchmark with public skills, structured semantic tags, a two-level taxonomy, training data, and thousands of evaluation queries \cite{cho2026skillret}. SRA formulates a broader pipeline in which skills are retrieved, incorporated, and applied from large external corpora \cite{su2026sra}. These papers establish skill retrieval as a standalone problem rather than a small prompt-engineering detail.

Scale and semantic confusability are related but not identical. Scale is the pressure created by many available skills and by the cost of exposing, embedding, ranking, or reranking them. Semantic confusability is the pressure created when several skills look relevant to the same request even though only one is procedurally correct. A large library makes confusability more likely because it increases the chance that multiple skills occupy the same domain, but a smaller domain-specific library can still be difficult if candidates share the same surface vocabulary. A library with many unrelated skills is mostly a search and context-management problem. A library with several similar PDF, spreadsheet, code-review, or deployment skills is a procedural disambiguation problem. This thesis is primarily concerned with the second failure mode: the wrong skill should often be plausible by topic, while the gold skill should be better because of an operational distinction.

\section{Operational Information in Skill Artifacts}

If semantic confusability is the core failure mode, the next question is what information might separate plausible near-neighbour skills. The field groups considered in this thesis should be understood as \emph{candidate operational information}, not as a claim that the thesis invents a universal skill schema or already knows which fields will work best. They are proposed axes along which two skills can be procedurally distinct: use condition, input or precondition, output artifact, workflow or procedure, dependency or resource requirement, boundary or not-for condition, and success or verification evidence. A difference on one of these axes matters only when it would change correct invocation, feasibility, execution path, output, or verification.

The conceptual skill literature motivates this operational view. Procedural-memory and SoK-style accounts imply that selecting a skill requires more than matching a topic: the selector must know whether the procedure applies, whether the expected inputs and resources are available, what actions the skill will perform, and what result counts as successful \cite{jiang2026procedural,jiang2026sok}. These are not merely formatting preferences inside a skill document. They are possible reasons why one skill should be invoked and another similar skill should not.

The Scheduling-Structural-Logical (SSL) representation provides a clear recent skill-specific schema example \cite{liang2026ssl}. SSL separates skill information into a scheduling layer, a structural layer, and a logical layer. Its scheduling layer includes signals such as supported intents, expected inputs, expected outputs, dependencies, and control-flow features. Its structural layer captures scene-level execution phases, while its logical layer records actions, resources, conditions, and effects. These categories overlap strongly with the thesis field groups. Use condition, input or precondition, output artifact, dependency or resource, workflow or procedure, and success or effect evidence should therefore be read as shared representational territory with SSL-like work, not as isolated labels invented here. The unresolved question is more specific: which of these information types are actually discriminative for routing when skills are deliberately near neighbours?

Public skill systems show why these signals are plausible but difficult to interpret. Anthropic-style filesystem skills may package instructions, scripts, resources, references, dependency instructions, and examples \cite{anthropic2025skills}. The Claude-skills ecosystem analysis shows that public skill libraries are uneven in length, redundancy, authoring style, and supply-demand balance \cite{ling2026claudeskills}. Real artifacts may therefore contain routing-relevant information, but it may be implicit, redundant, inconsistently named, or mixed with execution-support material. A use condition may appear as a trigger phrase, a warning, or a sentence inside the workflow. A dependency may be a hard routing constraint, a setup command, or merely an implementation note. A boundary may be explicit, such as a warning not to use a skill for regulated advice, or implicit, such as a skill only being safe for local files.

This matters because not every part of a skill artifact is equally useful for selection. Few-shot examples, sample commands, setup snippets, and reference links can help the agent use a selected skill, yet they do not necessarily define a different capability. Other information is closer to the invocation decision because it describes when a procedure applies, what it expects, what it produces, what it depends on, where it should not be used, or how success is recognised. The literature therefore motivates RQ1 without answering it. Existing work shows that skills are procedural artifacts, that structured schemas such as SSL expose operational information, and that public skill libraries contain such information unevenly. It does not yet determine which information types help distinguish semantically similar but procedurally distinct skills.

\section{Skill Representation and Retrieval Strategies}

The next literature question is how skill information is made usable for selection. This requires separating three objects that are often blurred together. A \emph{skill artifact} is the stored capability itself: a \texttt{SKILL.md} file, script, resource folder, generated program, prompt module, or other executable procedural package. A \emph{skill representation} is the selector-visible form of that artifact: a name, short description, full text body, structured field card, hierarchy node, or graph neighbourhood. A \emph{skill retrieval strategy} is the method that operates over those representations to choose candidates, such as flat lexical or dense matching over a text encoding, reranking a first-stage candidate set, traversing a hierarchy, or exploring a graph. This distinction matters because an experiment can improve selection by changing the artifact, by exposing a richer representation, or by using a stronger retrieval strategy.

Flat or unstructured retrieval is the first family. In this family, the selector sees a text encoding of the skill rather than an explicitly separated procedural structure. That encoding may be a short name--description pair, a longer metadata block, the full skill body, or a concatenation of selected fields. Lexical search, dense embedding retrieval, and simple hybrid retrieval are therefore matching variants inside the same family, not separate representation families: all rely on an unstructured or weakly structured text encoding. SkillAct is best read as a flat textual skill-representation baseline because skills are inserted into the agent prompt rather than retrieved through a learned index \cite{liu2024skillact}. Voyager stores executable programs as skill artifacts, but its retrieval-visible representation is compact: each program is indexed through a generated natural-language description and recalled by description-level similarity when a new task is attempted \cite{wang2023voyager}. These examples show why compact metadata is attractive. It is easy to author, easy to expose, and compatible with standard retrieval pipelines. They also expose the central uncertainty. A short description may be efficient but under-specify operational distinctions, while a full skill body may expose more information but increase selector-visible context, embedding cost, and retrieval noise.

Retrieve-then-rerank should be treated as a pipeline variation over this candidate set unless the reranker uses a different structured representation. SkillRouter, SkillRet, and SRA make this large-scale setting explicit by treating skill selection as retrieval, or retrieval followed by reranking, over large candidate pools \cite{zheng2026skillrouter,cho2026skillret,su2026sra}. A retrieve-then-rerank system first obtains a smaller candidate set using a cheaper flat matcher, then uses a stronger model or richer matching function to reorder candidates with more context. ToolRerank provides transferable evidence from tool retrieval that hierarchy-aware reranking can improve selection and downstream execution, while ToolRet cautions that generic retrieval models are not automatically well aligned with tool-like capability selection \cite{zheng2024toolrerank,shi2025toolret}. For skill retrieval, reranking is promising because it can inspect a smaller set of plausible candidates after a cheaper first-stage retriever. However, reranking does not remove the representation question. If the first-stage retriever fails to include the gold skill, or if the candidate representation hides the operational distinction, a reranker may not recover the correct skill.

Hierarchy, tree routing, and DAG-style orchestration sit between representation and retrieval. They can define what the selector sees, but they also define how candidates are traversed or filtered. Adjacent retrieval and tool-use work supports the general coarse-to-fine intuition. RAPTOR organises document chunks into a recursive summary tree and retrieves across abstraction levels rather than relying only on flat chunks \cite{sarthi2024raptor}. ToolChain* is closer to tool use: it represents possible API-call sequences as a decision tree and uses A* search to prune the action space, reducing exhaustive exploration while preserving a path toward a valid tool plan \cite{zhuang2024toolchain}. Skill-specific work makes a similar claim in the skill-retrieval setting. The single-agent skill-failure paper and AgentSkillOS suggest that coarse-to-fine selection can mitigate failures that appear when an agent chooses directly from a large flat pool \cite{li2026singleagent,li2026agentskillos}. The attraction is clear: hierarchy can reduce search space, context cost, and the number of decisions made at once. The risk is also clear. A hierarchy assumes that early routing choices are reliable and that the gold skill is reachable through the chosen branch. Real skill libraries may violate this assumption because skills overlap across domains, combine capabilities, or differ procedurally inside the same topical category.

Graph and relational approaches generalise this issue. RAG and tool-use work provide adjacent methodological support here. KG$^2$RAG starts from semantic retrieval, then expands and organises chunks through knowledge-graph relationships, showing how graph links can add structure after a flat first-stage retriever \cite{zhu2025kg2rag}. SciToolAgent provides a closer capability-selection example, where prerequisites, dependencies, compatibility, and safety constraints are represented in a graph for scientific tool use \cite{ding2025scitoolagent}. Skill-specific graph work applies the same idea directly to skills: SkillNet models skills through taxonomy, typed relations, and package structure, while knowledge-graph work on learned skills suggests that skill procedures can be decomposed into structured relational forms \cite{liang2026skillnet,learningkg2026}. Graphs are attractive because they can represent multi-parent membership, similarity, dependency, composition, resource use, and workflow compatibility without forcing a single tree path. However, graphs are only as useful as their nodes and edges. If graph edges are built from shallow semantic similarity, the graph may reproduce the same ambiguity that confused flat retrieval. If edges encode procedural relations, dependencies, boundaries, or outputs, the graph may support more targeted selection.

Structured field representations provide another representation choice. SSL is one clear recent example of converting text-heavy skill artifacts into linked scheduling, structural, and logical layers \cite{liang2026ssl}. This approach is relevant because it makes operational information more explicit before retrieval. A structured representation can in principle preserve inputs, outputs, dependencies, workflow phases, resources, conditions, and effects more compactly than a raw full document. Yet it also introduces new uncertainties. The schema must be extracted or authored reliably; the retriever must know how to use the fields; and the evaluation must distinguish the value of the structure from the value of simply adding more text. Structured representations therefore provide a plausible answer to the representation problem, but the literature has not yet fully separated field quality, extraction quality, retrieval strategy, and evaluation design.

The literature therefore motivates several RQ2 candidates rather than a single settled architecture. Plausible skill representations include unstructured text encodings, such as flat metadata or full-body text, hierarchy nodes, graph relations, and structured fields. Plausible retrieval strategies include flat lexical or dense matching over text encodings, retrieve-then-rerank pipelines, hierarchy traversal, graph traversal, field-aware matching, and hybrid pipelines. These choices differ in what information they expose, how much context they require, where they place the main selection decision, and what failure modes they create. The unresolved comparison is how different representation and retrieval strategies preserve, organise, or exploit the operational information introduced by RQ1.

\section{Public Skill Ecosystems and Noisy Authored Skills}

Public skill ecosystems add an important practical constraint. The data-driven analysis of Claude skills contributes ecosystem evidence rather than a new retrieval method \cite{ling2026claudeskills}. It measures properties of a large public skill collection, including redundancy, length variation, and supply-demand imbalance. This is relevant because it shows that real skill libraries are already noisy, redundant, and unevenly structured. Some skills are narrow and atomic. Others are broad wrappers, parent skills, documentation-heavy packages, or lightly modified variants of similar capabilities. Such variation makes retrieval both a scale problem and a representation-quality problem.

Public skills also show why extraction and normalisation may be needed. Real artifacts rarely contain only a name and one-sentence description. They often include use conditions, expected inputs, workflow instructions, output expectations, dependency notes, resource files, examples, setup commands, and warnings about when not to use the skill \cite{anthropic2025skills,ling2026claudeskills}. These elements can be candidate selection evidence, but they are not always cleanly labelled. For example, a dependency line such as an \texttt{npm install} command may simply support execution after a skill is selected, while a dependency on a specific platform, package version, account, or runtime may be a hard routing constraint. Similarly, a boundary warning may be decisive if it excludes legal, financial, medical, or destructive use, but weaker if it is a generic caution repeated across many skills.

This public-skill evidence supports the thesis decision to separate controlled near-neighbour experiments from public-gold and external-scale checks. The controlled setting isolates semantic confusability and field-level distinctions: non-target information can be held constant while one operational field is exposed or hidden. Public settings test whether the same ideas survive messier authored artifacts, broad parent skills, duplicate capabilities, and provider-specific names. The external SkillRouter-style benchmarks add further portability pressure, but they can differ from the local controlled setting in important ways, including prompt length, explicit file references, and how normalised the skill bodies already are. Public corpora therefore help test ecological validity, but they do not replace controlled field-isolation tests for RQ1.

\section{Evaluation Gaps}

One of the clearest gaps in the literature emerges when evaluation practices are examined closely. Existing work often reports overall task success, while fewer studies isolate retrieval quality itself. SkillsBench measures whether skills help, but not large-library disambiguation \cite{li2026skillsbench}. AgentSkillOS and SkillNet demonstrate strong system-level gains, but retrieval, orchestration, and planning improvements are partly entangled \cite{li2026agentskillos,liang2026skillnet}. The Claude-skills analysis documents redundancy, length variation, and ecosystem unevenness, but does not compare retrieval methods experimentally \cite{ling2026claudeskills}. The single-agent skill-failure paper directly targets semantic confusability, but it studies synthetic skill descriptors and a relatively simple hierarchy rather than field-level evidence from authored skill artifacts \cite{li2026singleagent}. Adjacent tool, document, and RAG retrieval work supplies useful ideas, but does not directly evaluate procedural skill artifacts \cite{sarthi2024raptor,zhuang2024toolchain,ding2025scitoolagent,zhu2025kg2rag,zheng2024toolrerank,shi2025toolret}.

Taken together, these works leave three gaps that map onto the two research questions. The first gap is field-level and motivates RQ1: existing work shows that skill bodies and structured skill representations can matter, but it does not isolate which operational information types carry discriminative routing value under semantic confusability. A benchmark may show that full skill text helps, or that a structured representation improves a task, without showing whether the decisive signal came from input requirements, output expectations, workflow steps, dependencies, boundaries, success criteria, or some other part of the artifact. The second gap is architectural and motivates RQ2: retrieval quality, representation design, reranking, orchestration, and downstream task success are often entangled. Some work begins to separate these stages, but system-level gains still do not always reveal whether improvement came from a better skill representation, a stronger first-stage retriever, a better reranker, or better use of the selected skill. The third gap is cost-related and also belongs to RQ2: even when efficiency is reported, cost is not consistently decomposed into comparable selector-visible tokens, candidate-budget size, retrieval latency, reranking cost, and amortised extraction or indexing cost.

These limitations mean that the thesis evaluation must separate several questions that prior work often combines. It must ask whether an operational field is discriminative at all; whether a representation exposes that field compactly and accurately; whether the first-stage retriever includes the gold skill in the candidate set; whether a reranker or field-aware matcher can order plausible candidates correctly; and what cost is paid at indexing time and at query time. This is why RQ1 and RQ2 are treated as equal rather than sequentially optional. RQ1 identifies which information is worth preserving for near-neighbour distinction. RQ2 asks which representation and retrieval strategies preserve, organise, or exploit that information reliably and efficiently.

\section{Synthesis and Research Questions}

The literature reviewed above points to a common problem but does not close it. Skills are reusable procedural capability units, not merely documents or atomic tools. Large libraries create both scale pressure and semantic confusability. Public skill artifacts contain operational information, but it is unevenly expressed and mixed with execution-support material. Structured representations, hierarchies, graphs, dense retrieval, lexical retrieval, and retrieve-then-rerank pipelines are all plausible responses, yet the literature does not clearly determine which operational information most effectively distinguishes competing skills or which representation and retrieval strategies use that information best.

This motivates the two revised research questions of the thesis:

\textbf{RQ1:} Which operational information types help distinguish semantically similar but procedurally distinct agent skills?

\textbf{RQ2:} How do skill representation and retrieval-pipeline choices affect the preservation and use of the routing-relevant operational information identified in RQ1 under semantic confusability, and what accuracy, candidate-recall, and retrieval-cost trade-offs result?

These questions arise from the literature rather than being imposed on it. Existing work has already shown that skills are useful, that flat selection becomes unreliable under scale, and that richer organisation may help. What remains unresolved is which information actually carries discriminative routing value, and how different retrieval strategies preserve or lose that value. The rest of the thesis therefore evaluates skill retrieval under semantic confusability: not merely whether a selected skill is broadly relevant, but whether it is the procedurally correct capability among plausible alternatives.
